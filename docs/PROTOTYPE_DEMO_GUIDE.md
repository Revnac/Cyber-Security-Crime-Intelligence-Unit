# Guardian AI - 15-Day Prototype Demonstration Guide

Version: (Date of completion of 15-day cycle)

## 1. Introduction

This document outlines key user flows and features to demonstrate in the 15-day prototype of the Guardian AI platform. The goal is to showcase the foundational capabilities for security event management, multi-currency transaction tracking, AML case management, and the integration with external services like Microsoft Sentinel.

**Prerequisites for Demo:**
*   Backend server running (`cd web_dashboard/backend && npm run dev`).
*   Frontend development server running (`cd web_dashboard/frontend && npm start`).
*   MongoDB instance accessible and configured in backend `.env` (`MONGODB_URI`).
*   **For Sentinel Integration Demo:**
    *   Backend environment variables for Sentinel correctly set (`SENTINEL_TENANT_ID`, `SENTINEL_CLIENT_ID`, `SENTINEL_CLIENT_SECRET`, `SENTINEL_GRAPH_API_ENDPOINT`).
    *   A test/dev Microsoft Sentinel instance with some sample alerts/incidents.
*   **For IP Geolocation Demo:**
    *   Backend environment variable `IPGEOLOCATION_API_KEY` set with a valid key from a service like `ipgeolocation.io`.
*   **For CSV Ingestion Demos:**
    *   Sample CSV files for crypto transactions and fiat transactions, formatted according to the expected headers (see `cryptoIngestionService.js` and `fiatIngestionService.js` for mapping details).

## 2. Key User Flows & Features to Demonstrate

### Flow 1: User Authentication & Authorization
1.  **Registration:** Show the user registration page (`/register`). Create a new user (e.g., an 'Analyst').
2.  **Login:** Log in with the newly created user and also with a pre-existing 'Admin' user.
3.  **Role-Based Access Control (RBAC):**
    *   Navigate to a view accessible by Analysts but perhaps with limited actions.
    *   Log in as Admin: Show an Admin-only section/feature (e.g., the "Admin Exclusive Section" placeholder on the main dashboard, or access to ingestion triggers).
    *   Demonstrate that certain API actions (e.g., deleting an AML case, if that were restricted) are blocked for non-Admin roles (can be shown via Postman or by disabling UI elements if implemented).

### Flow 2: Cryptocurrency Transaction Monitoring
1.  **(Admin) Crypto CSV Ingestion:** (If sample crypto CSV available)
    *   Navigate to where a crypto CSV upload UI would be (Note: We created the backend `/api/ingest/csv` but didn't explicitly build a dedicated UI for *crypto* CSVs in this phase. The `FiatCSVUpload.js` can serve as a demo for the upload mechanism concept).
    *   *Alternative for demo:* Manually insert some `CryptoTransaction` data into MongoDB if no upload UI is ready.
2.  **View Crypto Transaction List (`/crypto-transactions`):**
    *   Show the list of crypto transactions.
    *   Demonstrate pagination and basic filtering (e.g., by blockchain).
3.  **View Crypto Transaction Details (`/crypto-transaction/:txHashOrId`):**
    *   Click on a transaction hash to navigate to its detail page.
    *   Show all displayed fields: hash, blockchain, timestamp, inputs, outputs, value, fee, metadata.

### Flow 3: Fiat Currency Transaction Monitoring
1.  **(Admin/DataEntryClerk) Fiat CSV Ingestion (`/ingest-fiat-csv`):**
    *   Navigate to the "Ingest Fiat CSV" page.
    *   Select a sample fiat transaction CSV file and upload it.
    *   Show the success message and ingestion summary.
2.  **View Fiat Transaction List (`/fiat-transactions`):**
    *   Show the list of ingested fiat transactions.
    *   Demonstrate pagination and filtering (e.g., by currency code, type, account number).
3.  **(Future) View Fiat Transaction Details:** (Detail page not built in this phase, but mention it's a logical next step).

### Flow 4: AML Case Management
1.  **View AML Case List (`/aml-cases`):**
    *   Show the list of AML cases (these would be generated by the backend `amlEngineService` if crypto transactions trigger rules, or could be manually created for demo).
    *   Demonstrate filtering by status, priority, rule triggered.
    *   Show pagination.
2.  **View AML Case Details (`/aml-case/:id`):**
    *   Click on a Case ID to navigate to its detail page.
    *   Review all case information: status, priority, summary, assigned user, linked crypto/fiat transactions (if populated).
3.  **Manage AML Case (in Detail View):**
    *   **Add Note:** Add a new investigation note to the case. Show it appearing in the notes list.
    *   **Update Status:** Change the status of the case using the dropdown.
    *   **Assign User:** Assign the case to a (mock) user ID. Show the "Assigned To" field update.
    *   **Link Transactions (Manual):**
        *   Demonstrate linking an existing (mock) Fiat Transaction ID to the case.
        *   Demonstrate linking an existing (mock) Crypto Transaction ID/Hash to the case.
        *   Show the transaction appearing in the respective "Linked Transactions" list on the detail page.

### Flow 5: Security Event Monitoring & Sentinel Integration
1.  **(Admin) Trigger Sentinel Alert Ingestion:**
    *   Using a tool like Postman or curl, make a `POST` request to `/api/external-sources/sentinel/ingest-alerts`.
    *   Show the `202 Accepted` response.
    *   Check server logs to (conceptually) show the background process starting.
    *   *(This assumes a test Sentinel instance is configured and accessible by the backend).*
2.  **View Security Event List (`/security-events`):**
    *   Show the list of security events.
    *   Point out events with `eventSource` as 'Microsoft-Sentinel-alert' or 'Microsoft-Sentinel-incident'.
    *   Demonstrate filtering by `eventSource` or MITRE Tactic/Technique ID.
    *   Show the enhanced MITRE ATT&CK data display (clickable links to MITRE website).
    *   Note the conditional styling for Sentinel events.
3.  **View Security Event Details (`/security-event/:eventId`):**
    *   Click on an event to see its full details, including the `rawData` from Sentinel and the parsed MITRE mapping.

### Flow 6: Geolocation (Conceptual/If Data Allows)
1.  **IP Geolocation Proxy:**
    *   Explain that the system has a backend proxy for IP geolocation (`/api/util/ip-geolocation/:ipAddress`).
    *   If there's a way to input an IP address in the UI that uses `ip_geolocator.js` (not explicitly built yet, but the script exists), demonstrate its use. Otherwise, this can be shown via a direct API call using Postman.
    *   This requires `IPGEOLOCATION_API_KEY` to be set in the backend `.env`.

## 3. Talking Points for Future "Advanced" Capabilities

*   **AI-Powered AML Analytics (Step 13):**

    *   Mention the placeholder `amlAnalyticsService.js` and the concept of a dedicated Python ML service.
*   **Advanced Crypto Forensics UI (Step 9 continuation):**
    *   The backend `traceFunds` service is an initial version. Future work includes a UI to initiate traces and visualize the resulting graph of fund flows.
*   **LLM & NLP Security (Step 10):**
    *   Refer to the `README.md` section on LLM/NLP security, discussing potential use cases (report analysis, PII detection) and the placeholder `inputAnalyzerService.js`.
*   **Deeper SIEM/XDR Capabilities (Step 12 continuation):**
    *   Beyond Sentinel ingestion, future work includes more advanced correlation within our platform, custom dashboards for threat hunting based on MITRE, and potentially integrating other security data sources.
*   **Microsoft Ecosystem Integration (User Feedback):**
    *   Reiterate plans to explore deeper integration with Microsoft Defender XDR and Microsoft Entra ID for comprehensive threat protection and identity management.
*   **Multi-Currency Enhancements (Ongoing):**
    *   Continued refinement of how different crypto tokens and fiat currencies are handled, valued (e.g., real-time USD conversion for all transactions), and linked within investigations.
*   **API Security Hardening & Pen Testing (Step 15):** Proactive measures to ensure platform robustness.
*   **Scalability & Deployment (Step 16):** Preparing the platform for operational rollout.
